# Harness 开发与交付流程草案

状态：技术栈与 GitHub 策略已确认。一套 Python 后端、React 前端；测试通过后推送功能分支并创建 PR。

## 单项任务闭环

1. 将需求写成可观察的验收条件，记录不在范围内的行为。
2. 拆成可独立验证的小任务，明确允许修改的模块、接口和依赖。
3. Agent 阅读本仓库文档与相关代码，先补足契约和必要的失败测试，再实现功能。
4. 本地执行格式、静态检查、单元测试、契约测试和受影响的集成/端到端测试；对失败进行修复并重跑。
5. 审查差异、确认无凭据和生成物、记录测试证据；只有检查通过才提交并推送功能分支、创建或更新 PR。
6. CI 在 GitHub 重跑同一套门槛。失败则修复后重新提交；需求或架构变化同步更新文档。合并 `main` 由 PR 审核与检查门槛控制。

## 自动化门槛

- 后端：格式/静态检查、类型检查、pytest 单元与 API/数据库集成测试。
- 前端：lint、类型检查、组件测试、生产构建。
- 跨端：OpenAPI 契约检查、核心评测流程 E2E，以及前端类型与后端响应的一致性检查。
- 无外部付费模型、真实密钥或真实目标服务时也能完成 CI；另设显式触发的真实服务验证。
- GitHub Actions 只在所有门槛成功后允许后续交付步骤；失败时保留日志和报告。

Git 提交应按完成的任务切分，而不是每次保存文件都提交。当前环境已验证可推送功能分支并创建草案 PR；后续任务沿用这一流程。
